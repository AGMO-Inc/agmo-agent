# Brainstorming: 아이디어를 설계로

## 개요

아이디어를 자연스러운 대화를 통해 완성된 설계와 스펙으로 만든다.

현재 프로젝트 컨텍스트를 파악한 뒤, 질문을 하나씩 던져 아이디어를 구체화한다. 설계가 완성되면 사용자 승인을 받고, Obsidian에 기록한다.

<HARD-GATE>
사용자가 설계를 제시받고 승인하기 전까지 어떤 구현 스킬도 호출하지 않고, 코드를 작성하지 않으며, 프로젝트를 스캐폴딩하지 않는다. 프로젝트가 아무리 단순해 보여도 예외 없이 적용한다.
</HARD-GATE>

## "설계가 필요 없을 만큼 단순하다"는 착각

모든 프로젝트는 이 프로세스를 거친다. 투두 리스트, 유틸 함수 하나, 설정 변경 — 전부 해당된다. "단순한" 프로젝트야말로 검증되지 않은 가정이 가장 많은 재작업을 유발한다. 설계 문서가 몇 줄이 될 수는 있지만, 반드시 제시하고 승인을 받아야 한다.

## 체크리스트

반드시 순서대로 완료한다:

1. **프로젝트 컨텍스트 탐색** — 파일, 문서, 최근 변경사항 확인
2. **명확화 질문** — 한 번에 하나씩, 목적/제약/성공 기준 파악
3. **2-3가지 접근법 제안** — 트레이드오프와 추천안 포함
4. **설계 제시** — 복잡도에 맞게 섹션별로, 각 섹션 후 사용자 승인
5. **설계 문서 저장** — Obsidian vault에 Design 노트로 기록
6. **구현 전환** — writing-plans 스킬을 호출하여 구현 계획 생성

## 프로세스

### 아이디어 이해

- 현재 프로젝트 상태를 먼저 확인 (파일, 문서, 최근 변경사항)
- 질문은 한 번에 하나씩 던져 아이디어를 구체화
- 가능하면 객관식 질문을 선호하되, 개방형도 괜찮음
- 메시지당 질문 하나 — 더 파야 할 주제는 여러 질문으로 분리
- 목적, 제약사항, 성공 기준을 이해하는 데 집중

### 접근법 탐색

- 2-3가지 다른 접근법을 트레이드오프와 함께 제안
- 추천안을 먼저 제시하고 이유를 설명
- 대화체로 자연스럽게 옵션 설명

### 설계 제시

- 무엇을 만들지 이해했다고 판단되면 설계를 제시
- 각 섹션은 복잡도에 비례하여 분량 조절: 단순하면 몇 문장, 복잡하면 200-300단어
- 각 섹션 후 "여기까지 괜찮은지" 확인
- 아키텍처, 컴포넌트, 데이터 흐름, 에러 처리, 테스트 커버
- 이해가 안 되는 부분이 있으면 돌아가서 명확화

## 설계 완료 후

### Obsidian에 기록

`save-note` 스킬을 호출하여 Design 타입으로 저장한다. 직접 Obsidian 저장 로직을 실행하지 않는다.

### 구현 전환

- writing-plans 스킬을 호출하여 상세 구현 계획 생성
- 다른 구현 스킬은 호출하지 않는다. writing-plans가 다음 단계다.

## 핵심 원칙

- **질문은 하나씩** — 여러 질문으로 압도하지 않기
- **객관식 우선** — 가능하면 선택지 제공
- **YAGNI 철저히** — 불필요한 기능은 설계에서 제거
- **대안 탐색** — 항상 2-3가지 접근법을 제안한 뒤 결정
- **점진적 검증** — 설계를 제시하고, 승인 후 진행
- **유연하게** — 이해가 안 되면 돌아가서 명확화
